# coding-loop

メイン（判断・合格条件・完了判定）と worker（Scenario・テスト・実装・verify）の 2 役で回す。メインはコードを書かない。プロジェクトの CLAUDE.md に判定基準・検証コマンド・テストの置き場所の指定があれば、この本文よりそれを優先する。

このプラグインでは worker は `coding-loop:worker` という名前のエージェントとして入っている。Agent ツールの subagent_type にはこの名前を使う。

## 0. 強さと Scenario の要否を 1 行で宣言する
- A（フル）: 見える振る舞いが変わりテストを置ける変更。新機能・バグ修正。1〜6 を全部やる。
- B（ミニ）: 小さな変更。VISION ファイルは作らず述語 1〜2 個を宣言、テスト 1 本、赤→緑→verify。レビューは差分が大きいときだけ。
- C（省略）: 些末（typo・リネーム・コメント・ログ・整形・1 行設定）、使い捨て・調査、テストが作れないもの。そのまま実装し「省略、理由は○○」と添える。
- 迷ったら一段下げる。お金・認証・セキュリティ・個人情報・データ破壊が絡めば A に上げる。「ちゃんと」「テストも」で上げ、「軽く」「試すだけ」で下げる。
- 実行中に一段上げる合図: 同じ直しを 2〜3 回しても赤、触るファイルが想定超え、戻しにくい変更に手が伸びた、仕様と実コードの食い違い、条件をテストで書けない。自分からは下げない。
- Scenario は別軸。利用者から見える変化があれば B・C でも書く。
- 記録（6 参照）は A・B・C とも書く。

## 1. 目標を具体化する
対象、成功の状態、失敗の状態、検証コマンド（verify / test / lint / typecheck）を確かめる。不明点は AskUserQuestion で選択式に聞く。検証コマンドは CLAUDE.md、次に package.json 等から探す。

## 2. Scenario を書く（要のとき）
`features/<機能名>.feature` に日本語 Gherkin（1 行目 `# language: ja`）。1 ファイル 1 機能、1 Scenario は期待結果 1 つ。タグ `@X1` は機能名の頭文字と連番で全体一意（既存を見て決める）。非エンジニアの言葉で書き、関数名・内部状態は書かない。書くのは worker。features が無ければ作る。テスト基盤が無くても書き、直前に「自動テスト未対応」と理由を注記する。

## 3. VISION を書く（A のとき）
`docs/vision/<名前>.md` に書き、全文を見せて選択式で承認を得てから進む。正常 1・異常 1・境界 1 の 3 行から始めてよい。

```
# VISION — <名前>
## ゴール（1〜2 行）
## 合格条件
| ID | 検証 | 条件（○○すると △△ になる） |
| @X1 | 機械 | Scenario を書いた条件はそのタグを ID にする |
| N1 / E1 / B1 / S1 | 機械 | 正常 / 異常 / 境界 / 状態。機械で判定できるものを土台にする |
| Q1 | AI | 見た目・文言など機械で測れないものだけ |
## テスト方針（store・関数名などの内部名はここに書き、条件には書かない）
```

## 4. 赤→緑を worker に委譲する
委譲文に必ず書く: 目的、対象ファイル、合格条件（ID 付き）、検証コマンド、制約、下の「書き方の決まり」。
頼む順: 失敗するテストを書く → 実行して赤の出力を残す → 最小実装 → 緑 → verify exit 0 → 赤と緑の実行ログを添えて報告。
テスト名やタグに入れる ID は VISION の ID をそのまま使う（新しい番号を振らない）。
後付けテストになったら: 実装をわざと壊す → 対象テストだけ赤を確認 → 壊しを Edit で戻す（git checkout / restore は使わない）→ 緑。赤くならないテストは作り直す。
worker から「差し戻し」（重いと判明）が返ったら、強さを一段上げて 3 に戻る。
書き方の決まり: マジックナンバーは名前付き定数にする。責務を混ぜない。名前は外から見える動きで付ける。関数は短さのために切らず、上から下に読める形を優先する。切るのは 2 回以上使うときか固有の名前が付くときだけ。呼び出しを何段も飛ばない。

## 5. レビューと手直し
- 5a 往復: `/code-review`（効き目 high）。直すのは、本番でデータ破損・セキュリティ事故・停止に至るものと、利用者に見える不具合に直結するものだけ。修正は worker。上限 3 回。同じ指摘が 2 回続いたら止めて相談する。
- 5b 手直し 1 回: 往復が止まったら `/simplify` を 1 回かけ、verify が緑なら終わり。再レビューはしない。
- Codex による別モデルのレビューは、A でお金・認証・データが絡むときだけ任意で足す。

## 6. 完了を判定して記録する
順に確かめる: (1) verify exit 0 (2) VISION の各 ID にテストがあり緑 (3) assert が条件の本質を見ている（クラス名の有無や見出しの出現だけの assert は不合格） (4) 見える挙動が変わる A は `/run` で実物を 1 回動かして観測する。スタブや途中画面を完走と呼ばない (5) 5b の simplify を 1 回かけて緑を確かめた (6) 記録に 1 行追記。
コミットと push は指示があってから。
記録は `~/.claude/logs/coding-loop.tsv` に 1 行（タブ区切り）。列は `日付 プロジェクト 強さ Scenario 赤確認 レビュー回数 直した指摘の件数 結果 備考`。
例: `2026-09-17	nekonote	A	要	済	1	0	完成	`

## テスト基盤が無いとき
3 つを実物で確かめる: 自分の管理のリポジトリか（origin・README）、CI やデプロイの設定が新しいフォルダを巻き込むか、node のバージョンや言語が衝突するか。1 つでも当たれば別リポジトリ `../<名前>_testkit`、当たらなければ本体内の `tests/`（専用の package.json と .node-version）を推奨し、選択式で決める。決定は CLAUDE.md に「テストの場所・verify コマンド・マージ順（本体→テストキット）」として書き、以後は聞かない。

## やらないこと
- 合格条件を書く前に実装する。見える変化があるのに Scenario を後回しにする。
- 赤を見ずにテストが通ったとする。テストを消す・条件を削る・上限を黙って増やす。
- 書いた本人に採点させる。レビューの往復を自作する。
- git checkout / restore / stash で作業ツリーを戻す。`git add -A` でまとめて add する。
- 中小規模の A で計画を別のエージェントに分ける。
