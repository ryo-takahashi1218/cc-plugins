# 合格条件・述語の書き方（非エンジニアにも分かる言葉で）

VISION や合格条件の述語（「○○すると △△ になる」）は、**非エンジニアが読んで何のことか分かる言葉**で書く。
利用者が画面で見る/操作する内容で表す。

## 厳守事項

- **プロジェクト固有の内部名を述語に入れない**：`store`・状態管理・関数名・内部変数・`origin=user` のような内部値。
  → 捨てるのではなく、「テスト方針（どう assert するか）」側に書いて保持する（**情報は捨てない**）。
- **汎用UI用語は使ってよい**：`textarea`・クリック・フォーカス・`blur`・Enter など、どのアプリでも通じる言葉。

## 例

- ✗ `保存→解除＋store更新(origin=user)`（内部の仕組みが混入していて、依頼者が読めない）
- ○ `保存すると編集が終わり元の表示に戻る`（外から見える結果＝述語）
  ＋ テスト方針に「保存時 store が origin=user で更新される」と書いて内部情報を保持。

## 理由

述語は「外から見える合格条件」。内部実装の名前を混ぜると、実装が変わるたびに条件も揺れ、独立した合否判定にならない。
非エンジニアの依頼者がレビューできる言葉にしておくことで、合意のズレも防げる。
（詳しい手順は loop-engineering スキル STEP2 を参照。）
