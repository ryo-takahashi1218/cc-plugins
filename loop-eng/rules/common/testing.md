# テスト方針（言語非依存）

全プロジェクト共通のテスト原則。コード例は含まない。

## BDD（ユーザーに見える振る舞いを先に決める）

ユーザーが操作または観測できる**新機能・バグ修正**では、実装前に振る舞いを Gherkin の Scenario として `features/<機能名>.feature` に書く。Scenario は受け入れ基準の正本であり、将来は QA 仕様書（living documentation）の元になる。

- 1 feature file = 1機能、1 Scenario = 1 QA項目（1つの期待結果）
- Scenario は非エンジニアが読める言葉で書く。関数名・store・内部状態などの実装名は書かない
- ID は Scenario の直前に `@R1` のようなタグで付け、カタログ全体で一意にする
- タグの接頭辞は機能名の頭文字を使う（例: recording → `@R1`）。既に別の機能で使われている文字なら、機能名の2文字目以降から選ぶ。使う文字自体に制限はない（他の機能と重複しなければよい）
- 新しくタグを振るときは既存の `features/` を見て、使われている文字と最大連番を確認する
- 対応する自動テストは、テスト名またはテストのタグに同じタグ（例 `@R1`）を含めて紐付ける
- 各 Scenario には、少なくとも1本の適切な自動テストを対応させる。主要導線・実アプリ依存は E2E、それ以外は統合テストまたはユニットテストで検証する。BDD と E2E は同義ではない
- テスト基盤が無くて自動テストを作れない場合も Scenario は書き、Scenario の直前にコメントで「自動テスト未対応」とその理由を注記する
- 内部実装のみの変更、文言・コメント、設定、使い捨て作業など、ユーザー可観測な振る舞いを変えないものには Scenario は不要

最小テンプレート（日本語 Gherkin）:

```gherkin
# language: ja
機能: <ユーザーの目的>

  @<一意なID>
  シナリオ: <利用者から見た振る舞い>
    前提 <開始条件>
    もし <利用者の操作または起きた出来事>
    ならば <観測できる結果>
```

## BDD → TDD の順序

BDD は「何を満たせばよいか」、TDD は「それをどう自動検証して実装するか」を担う。対象となる変更は、**BDD Scenario → レッド → グリーン → リファクタ**の順で進める。

## レッド→グリーン→リファクタの原則

新機能・バグ修正は必ず以下の順で行う:

1. **レッド**: まず失敗するテストを書く（実装前にテストが赤くなることを確認する）
2. **グリーン**: テストが通る最小限の実装を書く
3. **リファクタ**: テストが緑のままコードを整理する

## 例外と後付けテストの扱い

レビュー指摘修正等でテストと実装を同時に変更しなければならない場合でも、可能な限りテスト変更を先に適用して赤を目視してから実装を変える。

やむを得ず実装より後にテストを書いた場合（後付けテスト）は、**ミューテーションチェック**でレッドを事後証明する。

## ミューテーションチェックの手順

後付けテストが本当に実装を監視できているかを確認する手続き:

1. 対象テストが守るべき重要ポリシー行を一時的に壊す（最も自然な後退: 削除・条件を無効化・分岐を固定値に）
2. 対象テストファイルのみ `npx vitest run <file>` を実行し、テストが赤くなることを確認する
3. 自分が入れた壊し編集を Edit で正確に逆適用して戻す。`git checkout` / `git restore` 等の巻き戻しコマンドは使わない（未コミットの実装や人の手による編集ごと消すため）
4. 対象テストが再び緑になることを確認する
5. 赤くならなかったテストは検出力ゼロ（偽パス）と判断し、ミューテーションが赤くなるようテストを作り直す

## 偽パステストの判断基準

ミューテーション後も緑のままであれば、そのテストは「実装に合わせて書いたから通っているだけ」の可能性がある。具体的には:

- テストが実装の変異を全く検出できない（決定表の迂回など）
- assert が常に成立するような期待値になっている

偽パスと判明したテストは必ず作り直し、同じミューテーションで赤くなることを確認してからコミットする。

## 完成の判定と危険な副作用

- 利用者が操作または観測できる機能の完了判定は、実際のアプリを動かす自動テストで検証する
- 外部への課金や送信のような危険な副作用を持つ改修は、赤いテストを書く前に副作用を差し替えられる口を先に作る
- 時間のかかる処理を伴う機能は、少なくとも1本のテストで本物の処理が最後まで完走し結果が画面に出ることを確認する。代役データや途中経過の表示だけを完走の証明として扱わない
- 画面表示や外部処理の実行が絡む変更は、コミット前に実際に動かして確認する。部品単位のテストが緑なだけでコミットせず、見た目に関わる変更は実際に描画して目視する
- スクロールに追従する固定表示の実装は、開始と終了の2点だけの座標比較で完了と判定せず、スクロール中の複数時点を画像で確認する
- 動きを伴う機能は、静止画1枚や分類名を付けただけで完成としない。位置や向き、段階的な変化を複数の時点で数値で確かめる

## テストの扱い

- 一度書いたテストは削除・無効化で放棄せず、赤くなった原因を直して緑にする。機能自体を取りやめる場合だけ例外だが、その場合も取りやめた理由を残す
