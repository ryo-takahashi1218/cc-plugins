# loop-engineering — 検証付きの自律ループで「誰でも」作る/直す

このスキルは、プログラミングが初めての人でも **クローズドループ(検証付き自律ループ)** を回せるようにする案内役です。あなた(Claude)は、利用者に専門知識がない前提で、噛み砕いて・順番どおりに・確認を取りながら進めてください。

> **このスキルが起動した時点で「やってほしい」という依頼は受領済み**です。VISION 作成・テスト追加・実装の編集・検証コマンドの実行はこの範囲で行ってよい。
> ただし **破壊的な操作(git commit/push・マージ・既存ファイルの大量削除・DB/本番への変更・デプロイ・`package.json` 等の設定変更・依存追加)は、その都度かならず利用者に確認**してから行います。勝手に進めないこと。

---

## 全体像(STEP 0 で強さを選んでから 1〜6)

```
[STEP 0] 適用判断(A/B/C)          … タスクの大きさで フル/ミニ/省略 を自動で選ぶ(★最初に必ず)
[STEP 1] 目標を聞き出す            … 何を作る/直すのかを具体化
[STEP 2] VISION.md を書く          … 合格条件を機械でも ○× 判定できる述語で列挙(★核心)
[STEP 3] テスト観点を洗い出す       … VISION の各行 = テスト1個 に展開(同じ ID で貫通)
[STEP 4] レッド→グリーン           … 先に赤を出す → 最小実装で緑 → npm run verify が exit 0
[STEP 5] 作る↔確認ループ           … 「指摘→修正」の往復は /loop-eng:review-loop に委譲(自作しない)
[STEP 6] 完了判定(Stop condition) … verify が exit 0 + VISION の全[機械]条件が緑 + reviewer が NO_ISSUES
```

**重複しない設計(重要):** STEP 5 の「指摘→修正の往復」は **このスキルで作り直さない**。既存の **`/loop-eng:review-loop` コマンド**に委譲する。ただし **「VISION の各条件が満たされたか」「`npm run verify` が exit 0 か」の判定は委譲先がやってくれない**(reviewer はコード品質しか見ない)。そこは **loop-engineering 自身が STEP 4 / STEP 6 で担保**する。

各ステップ末には **「✅ これが出たら次へ」** を置く。迷ったらそこで利用者に確認すること。

---

## STEP 0: 適用判断(まず“どの強さでやるか”を決める)★最初に必ず

タスクを受け取ったら、いきなり VISION を書き始めず、まず **強さ(A/B/C)を判定**し、選んだ理由を1行で利用者に伝える。「実装して」「直して」等で起動しても、**毎回フルでやらない**ためのゲート。

- **A:フルループ** — 新機能・バグ修正など **観測可能な振る舞いが変わり、テストを置ける**変更。→ STEP 1〜6 を全部やる。
  - **A-中小(1〜数ファイル)= 既定**。計画も実装もメイン会話でインライン。**分離はしない**(ハンドオフで意図が欠落し往復が増えるだけ)。
  - **A-大(多ファイル/移行/仕様が重く 1 コンテキストに載らない)= 規模が要求するときだけ**。計画を Plan エージェント(PMロール)に分離し、人間承認ゲート + workflow `loop-eng:loop-engineering-large-A` に乗せる。詳細は後半の **「大規模A(A-大)のオーケストレーション」** 節。
- **B:ミニループ** — 小さい変更(小分岐の追加・軽い修正など)。→ VISION.md ファイルは作らず、**述語を1〜2個その場で宣言 → テスト1個 → 実装 → `npm run verify` で exit 0** まで。レビュー往復(`/loop-eng:review-loop`)はリスクや差分が大きいときだけ。完了判定は簡略(verify 緑＋宣言した述語が緑)。
- **C:省略(そのまま実装)** — 次のいずれか。普通に実装し、**「ループは省略しました(理由: ○○)」と一言添える**(Scenario: 要/不要 も添える。要ならどのファイルにどのタグで書いたか):
  - 些末(typo・リネーム・コメント・ログ・整形・1行設定)
  - 使い捨て/お試し/調査(「ちょっと試して」「叩き台」)
  - 非コード(ドキュメント・設定・インフラ)や、**テストが原理的に作れない/テスト基盤が無い**

**判定のコツ:**
- **迷ったら一段下げる**(A↔B 迷い→B、B↔C 迷い→C)。重さは後からいつでも上げられる。
- ただし **データ破壊・課金・認証・セキュリティ・お金や個人情報**に関わる変更は、小さく見えても **A に上げる**。
- 利用者の言葉で動的に変える:「ちゃんとやって」「テストも」→格上げ / 「軽くでいい」「試すだけ」→格下げ。

**実行中の格上げ(上り階段)**:着手後に次の兆候が出たら強さを一段上げる(C→B→A)——(1)手戻り:同じ直しを2〜3回しても赤のまま／設計・前提級の重い指摘 (2)広がり:触るファイルが想定を超えて増えた (3)不可逆:戻しにくい変更に手が伸びた (4)曖昧:仕様が実コードと食い違うと判明 (5)検証不能:条件をテストで表現できない・テストが不安定。上げるときは理由を1行宣言する。**自分からは下げない**(利用者の「軽くでいい」は別)。格上げしても完了条件は緩めない。

**Scenario の要否も同時に判定する(A/B/C とは別軸)**:強さ(A/B/C)は**作業の重さ**、Scenario の要否は**利用者から見える変化があるか**で決まる別の軸。**B・C でも見える変化があれば Scenario は要る**(小さい修正でもボタンの挙動が変われば QA 項目になるため)。要否の基準と書き方の規約は **同梱の `${CLAUDE_PLUGIN_ROOT}/rules/common/testing.md` の BDD 節が正本**。このスキルで再定義しない。「要る」と判定したら、**A/B/C のどれであっても、実装より先に(C でそのまま実装する場合も、実装に入る前に)`features/<機能名>.feature` に Scenario を書く**。

**✅ これが出たら次へ:** A/B/C を決め、理由を1行で伝えた。**Scenario の要否も宣言した。** A → STEP 1 へ / B → STEP 2(簡略)へ / C → そのまま実装して省略を明記。

## STEP 1: 目標を聞き出す(具体化する)

初心者は「何を伝えればいいか」が分からない。**あなたから順に質問**する(一度に全部聞かず 1〜3 問ずつ)。

**聞くこと(テンプレ):**
1. **何を作りたい/直したいですか?**(例:「保存ボタンを押すと入力が消えるバグを直したい」)
2. **うまくいったと言えるのはどんな状態ですか?**(例:「保存後も入力が残る」)
3. **逆に、こうなったら失敗、という状態は?**(例:「空のまま保存できてしまう」)
4. **対象のファイル/フォルダはどこですか?**(分からなければ「一緒に探します」と言って Glob/Grep で探す)
5. **使えるチェックコマンドはありますか?**(`npm run verify` / `npm test` / `npm run lint` / `npm run typecheck` 等。分からなければ自分で `package.json` 等を読んで調べる)

> **答えられないときの逃げ道:**「では似た例を 2〜3 個こちらから挙げます。近いものを選んでください」と **選択肢を出す**。ゼロから言わせない。

**プロジェクトの土台を自分で調べる(初心者の代わりに):** `package.json` / `pyproject.toml` / `Makefile` 等を読み、`test` / `lint` / `typecheck` / それらをまとめた `verify` があるかを把握する。**設定ファイルは勝手に書き換えない**(追加は提案 → 承認後)。

**✅ これが出たら次へ:** 「作る/直す対象」「成功イメージ」「失敗イメージ」が一文ずつ言葉になり、対象の場所と使える検証コマンド(または個別ゲート)が分かった。

## STEP 2: VISION.md を書く ★このスキルの核心

**VISION.md = 「何ができたら成功か」を観測可能な述語だけで書いた合格条件書。** これがループの「ゴールテープ」。これが無いとループは終われない。時間をかける。

### 良い述語 / 悪い述語

| 悪い(測れない) | 良い(観測可能な述語) |
|---|---|
| 入力を使いやすくする | `N1 [機械]` 有効なメールで送信すると 200 と `{ok:true}` が返る |
| エラーをちゃんと出す | `E1 [機械]` メール欄が空で送信すると 400 と `{error:"required"}` が返る |
| 変な値に強くする | `B1 [機械]` 上限255字ちょうどは成功し、256字は 400 になる |
| ログイン状態を保つ | `S1 [機械]` ログイン後にリロードしても認証済み画面が表示される |
| 見た目を整える | `Q1 [AI]` 送信ボタンは無効時にグレーアウトし、押下不可と分かる |

コツは **「○○すると △△ になる」** の形で、**外から見て確かめられる結果**を書くこと。

> **述語は非エンジニアが読んで分かる言葉で書く。** 利用者が画面で見る/操作する内容で表す。**プロジェクト固有の名前(store・状態管理・関数名・内部変数・`origin=user` のような内部値)は述語に入れない** → それらは「テスト方針」(どう assert するか)側に書いて保持する(情報は捨てない)。`textarea`・クリック・フォーカス・`blur`・Enter のような**どのアプリでも通じる汎用UI用語は使ってよい**。例: `保存→解除＋store更新(origin=user)`(✗ 内部が混入)→ `保存すると編集が終わり元の表示に戻る`(○ 述語)＋ テスト方針に「保存時 store が origin=user で更新される」。

### 各条件に振る 2 つのラベル

1. **ID**(カテゴリ頭文字+連番)。VISION → 観点表 → テスト → 完了判定まで **同じ ID で一気通貫**させる。
   - `N` = 正常系(Normal) / `E` = 異常系・エラー処理(Error。例外時の振る舞いも E に含める) / `B` = 境界値(Boundary) / `S` = 状態(State)
   - (任意)`Q` = 見た目・文言など曖昧な品質
2. **検証手段タグ**(誰が ○× を出すか)。
   - `[機械]` = テスト/lint/型チェックで自動判定できる(**最優先で土台にする**)
   - `[AI]` = 機械で原理的に測れないものだけ AI に採点させる(**乱用しない**)
   - **迷ったら必ず `[機械]` に寄せる。**

**Scenario を書いた条件は、そのタグを VISION の ID 欄にそのまま書く**(`@R7` のように `@` 付きで書き、VISION 独自の条件 `N1`/`E1`/`B1`/`S1` と表記で見分ける)。新しい ID 体系を作らない。これで **Scenario → VISION → テスト → 完了判定が同じ ID で一直線**になり、あとで `features/` を集約したとき「どの QA 項目がどのテストで守られているか」がタグで追える。

> **A-大(workflow `loop-eng:loop-engineering-large-A`)は例外**:plan モードが ID を axis ごとに機械的に振り直すため、Scenario タグを ID にできない。A-大では各条件の `testIdea`(テスト方針)に「対応 Scenario: @R7」と書いて持たせる。
> 明示のフィールド `scenarioTag` に入れる形を推奨する(`testIdea` の書き方も引き続き受け付ける)。

### VISION.md テンプレ(そのままコピーして埋める)

```markdown
# VISION — <機能/修正の名前>

## ゴール(1〜2行・人間向け)
<このタスクが達成された世界を一言で>

## 完了条件(Stop condition)
- [ ] `npm run verify`(typecheck && lint && test 相当)の exit code が 0
      ※ まとめコマンドが無い場合: typecheck / lint / test を個別実行し全部 exit 0
- [ ] VISION の全 [機械] 条件に対応するテストが存在し、緑である(同一 ID で照合)
- [ ] reviewer が `NO_ISSUES`(CRITICAL/HIGH の指摘ゼロ)
- [ ] (`[AI]` 条件がある場合のみ)AI 検証がすべて pass
- [ ] (A で観測可能な挙動が変わる場合)実物を1回動かして観測し期待どおり
- [ ] 往復は最大 5 回。超えたら止めて人間に相談

## 合格条件(=テスト観点=テスト。すべて同じ ID で貫通)
| ID | 検証手段 | 条件(○○すると △△ になる) |
|----|----------|------------------------------|
| N1 | [機械]   | <正常系> |
| E1 | [機械]   | <異常入力 → 期待されるエラー> |
| B1 | [機械]   | <境界値ちょうど / +1 の挙動> |
| S1 | [機械]   | <状態遷移・連続操作・永続化> |
| Q1 | [AI]     | <見た目/文言など曖昧な品質。無ければ省略> |
```

> **初心者がつまずく所:**「全部の条件を最初から完璧に出さなきゃ」と固まる。→ 不要。**正常系1・異常系1・境界1 の3行だけでもまず書けば回り始める**。後から足せる。最初の1行は一緒に書いてあげる。
> **保存と承認:** プロジェクトの分かりやすい場所(`VISION.md` or `docs/VISION-<名前>.md` or `docs/vision/<名前>.md`)に置く。新規作成は破壊的ではない。既存の同名があれば上書き確認。作ったら**全文を見せて「この条件でOK?抜けは?」と承認をもらう**。
> **中小規模でも守るガード:** 後半の「大規模A(A-大)のオーケストレーション」節にある**全 A で守る3つのガード**(赤テストが書けることが前提/承認ゲートで暗黙前提を拾う/戻りチャネル)は、A-大に限らず**中小規模の A でもそのまま適用**する。

**✅ これが出たら次へ:** ID + 検証手段タグ付きの合格条件が最低3行あり、各行が「○○すると △△ になる」の機械判定できる言い切りで、完了条件節が埋まり、利用者が承認した。

## STEP 3: テスト観点を洗い出す(VISION → テストへ展開)

VISION の各行を **テスト1個**に落とす。**ID は VISION と同じものを使い回す**(N1 の条件 → N1 のテスト)。これで「条件 ↔ 観点表 ↔ テスト」が同じ番号で一直線になり、抜け漏れと迷子を防ぐ。

### 5 つの軸(出発点。完全網羅ではない)

各入力にこの軸を順に当てて「テストすべき状況」を機械的に出す:

| 軸 | 接頭辞 | 何を問うか | 例(メール入力) |
|----|--------|-----------|----------------|
| 正常系 | N | 普通の入力で期待どおり動くか | 正しいメール → 成功 |
| 異常系 | E | 不正・想定外で安全に失敗するか | 空 / 形式不正 / 型違い → 期待エラー |
| 境界値 | B | 端っこで壊れないか | 255字 OK / 256字 NG、0件 / 1件 |
| 状態 | S | 前後の状態・連続操作・永続化は | 連続送信、リロード後、重複登録 |
| エラー処理 | E | 失敗が握り潰されず伝わるか | 依存先ダウン時に 500 でなく 503+案内 |

> 4〜5 軸は「考え始める足場」であって完全網羅の保証ではない。各入力に当てた後、「この軸では拾えない固有のリスクは?」を一度だけ自問して追加する。1条件がテスト1個に収まらなければ `N1-a` `N1-b` と枝番で割る。

### テストの置き場所を確認

既存テスト(`*.test.ts` / `*_test.py` / `tests/` 等)を Glob で探し、そのプロジェクトの流儀に合わせる。テスト実行コマンドを確定する。テストが1つも無いなら最小の1ファイルから(フレームワークは既存依存から判断、無ければ確認)。

**✅ これが出たら次へ:** VISION の各 ID に対応するテスト方針(どのファイルに何を assert するか)が決まり、テスト実行コマンドが確定した。

## STEP 4: レッド → グリーン(ここはこのスキルが直接やる)

**同梱の `${CLAUDE_PLUGIN_ROOT}/rules/common/testing.md` に厳密に従う:レッド → グリーン → リファクタ。**

### 機能追加
1. 観点表の `[機械]` 行を、**実装より先に失敗するテスト**として書く。
2. 実行して **赤(失敗)になることを目視**する。赤くならないテストは検出力ゼロ(偽パス)→ 書き直す。
3. 通る **最小限の実装**を書く(グリーン)。緑のまま整える(リファクタ)。

### バグ修正
1. **バグを再現する失敗テストを先に書く**(レッド)= バグの述語化そのもの。
2. 赤を確認 → 最小修正でグリーン。

### 後付けテストになった場合(ミューテーションで事後証明)
実装が先行した/既存実装にテストだけ足す場合は、検出力を事後証明する:
1. テストが守るべき実装の重要行を**わざと壊す**(削除/条件無効化/分岐を固定値に)。
2. 対象テストだけ実行し、**赤くなることを確認**(`npx vitest run <file>` 等)。
3. 自分が入れた壊し編集を **`Edit` で正確に逆適用して戻す**。`git checkout` / `git restore` 等の巻き戻しコマンドは使わない(未コミットの実装や人の手による編集ごと消すため)。
4. 再び緑に戻ることを確認。
5. 赤くならなければ偽パス。同じミューテーションで赤くなるよう作り直す。

> なぜ赤を先に見るのか:**テスト自身がちゃんと働いている証拠を先に取る**ため。赤を一度も見ていないテストは「実装に合わせて書いただけ」で回帰を検出できない飾りになりがち。

仕上げに **`npm run verify`(typecheck && lint && test 相当)を実行し exit 0** を確認する。まとめコマンドが無ければ typecheck → lint → test を個別実行し全部 exit 0。

**✅ これが出たら次へ:** 最初に書いたテストが全部緑で、`npm run verify` が exit 0。

## 検証ゲートは 2 種類(役割を間違えない)★中核

| | 機械的検証 | AI 検証 |
|---|---|---|
| 中身 | テスト / lint / 型チェック | LLM に見た目・文言・トーンを採点させる |
| 性質 | **決定的・安い・回帰に強い** | 非決定的・ブレる・高コスト |
| 判定 | **exit code 0 / 非0** で自動 | 合否/スコアを文章で |
| 位置づけ | **土台(必須)** | **上乗せ(曖昧な品質だけ)** |

原則:**土台は機械的検証**。AI 検証は VISION の `[AI]` 行だけに使い、機械で測れるものを AI 任せにしない。

---

## STEP 5: 作る↔確認ループ(/loop-eng:review-loop に委譲。作り直さない)★中核

STEP 4 で「最初のテスト+実装が緑、`npm run verify` が exit 0」になったら、ここからの **「厳しくレビュー → 直す → 再レビューを指摘0まで」の往復**は、**自前で実装せず `/loop-eng:review-loop [最大回数]` コマンドに委譲**する。これが maker/checker 分離(作る人に自己採点させない)を効かせる実体になる。

### 委譲先＝`/loop-eng:review-loop`

- **委譲先は `/loop-eng:review-loop [最大回数]`(既定 5)**。`loop-eng:reviewer` が指摘し、`loop-eng:fixer` が直す往復を指摘0まで回す。
- 実体は**スラッシュコマンド**(`Skill(...)` では呼べない)。呼び出し I/F は `/loop-eng:review-loop [最大回数]`(不変)。
- ループ内部仕様(「同じ指摘が2回連続で停止」「NO_ISSUES 終了」「履歴が肥大したら要約」)は **コマンド側が持つ**。loop-engineering は二重実装せず、結果を受け取るだけ。

### `/loop-eng:review-loop` の渡し方(親が保持する)

- **親オーケストレータが SCOPE/FOCUS/履歴を保持し、`loop-eng:reviewer` → `loop-eng:fixer` を指摘0まで回す**手順。**loop-engineering 自身がその親**になる(中身が見えないブラックボックスを呼ぶのではない)。
- 起動前に決めておくもの:
  - **SCOPE** = レビュー対象(STEP 1 で決めたファイル・フォルダ・差分)。
  - **FOCUS** = 重点観点(任意。例「セキュリティ重点」)。無ければ `loop-eng:reviewer` のデフォルト観点。
  - **最大回数** = VISION の往復上限(既定 5)。**コマンド引数で渡せるのはこれだけ。**
- ⚠️ **VISION.md や完了条件(verify exit 0)はコマンドに渡せない**(受け口が無い)。それらは loop-engineering 側が保持し、**STEP 6 で自分で照合**する。reviewer 起動時の FOCUS や根拠としてプリアンブルに注入はできる。

### reviewer / fixer の実際の挙動(コマンドが中で回す。再定義しない)

- **`loop-eng:reviewer`(確認担当 / checker):** バグ・並行性・セキュリティ・パフォーマンス・設計の**純粋なコードレビュー**。出力は機械可読で、**CRITICAL/HIGH のみ列挙、無ければ `NO_ISSUES` の1行**だけ。**`npm run verify` や exit code や VISION は見ない**(だから verify と VISION 照合は loop-engineering の仕事)。
- **修正役 `loop-eng:fixer`(実装担当 / maker):** 指摘を **1 件ずつ最小修正**。バグはレッド→グリーン、後付けはミューテーションで検出力確認、修正後に **`npm run verify` で exit 0** を確認。**誤った指摘には従わず、理由を添えて報告**する。
- コマンドは **「同じ指摘が2回連続なら停止」「履歴が肥大したら要約」** を内蔵している。loop-engineering は二重に実装せず、**結果(NO_ISSUES か、上限/重複で停止か)を受け取るだけ**。

### 最終通しレビュー(コミット刻みの穴を塞ぐ・全タスク完了後に1回)

「1タスク→レビュー→コミット」で刻む運用(loop-eng:coding-orchestrator 経由)では、各回のレビューが**その回の変更だけ**を見るため、**コミット済みの前タスク分がレビュー視界から消える**。この穴(タスク間の不整合を誰も見ない)を塞ぐため:

- **ループ開始時**(最初のタスクに着手する前)に `START_SHA=$(git rev-parse HEAD)` を控える。
- **全タスク完了後・STEP 6 の完了判定に入る前に1回だけ**、SCOPE を `git diff START_SHA..HEAD` にして通しレビューを1回走らせる(タスク間の整合を確認する目的。往復を回すためではない)。
- 指摘が出たら**通常の修正フロー(STEP 4 → STEP 5)に戻して**直し、緑にしてから完了判定へ進む。

**✅ これが出たら次へ:** レビューが `NO_ISSUES` で戻り(または上限/重複で停止 → STEP 6 のエスカレーション)、最終通しレビューでも新たな不整合が出ない。

## STEP 6: 完了判定(Stop condition)★中核

レビュー(`/loop-eng:review-loop`)が NO_ISSUES で戻っても、**「VISION の全条件が満たされたか」「verify が exit 0 か」は誰も担保していない**(reviewer はコード品質しか見ない)。だから完了判定は **loop-engineering 自身が次の順で行う**(この順番は reviewer の仕様ではなく**このスキルのポリシー**)。観測可能な挙動が変わる変更では、テスト緑だけで終わらせず**ビルトインの verify スキルで実物を1回動かして見る**ところまでが完了判定に含まれる。

1. **まず機械的ゲート:** `npm run verify` の exit code。**0 以外なら未完** → STEP 4 へ戻る(壊れているコードの見た目を褒めても無意味)。
2. **緑のときだけ、VISION の各 `[機械]` 条件に対応するテストが存在し緑かを同一 ID で照合。** 照合は存在と緑だけでなく、**テストの assert 内容が述語の本質を検証しているか**を読み比べる。クラス名の有無・骨組み見出しの出現など**弱い代理だけの assert は不合格**とし、テストを直す。動き・アニメーション系は途中を複数コマ＋座標/中間値/方向で assert する。
3. **最後に `[AI]` 条件だけ**、見た目/文言を AI に採点させる。

### 完了条件(これが全部 ○ なら「完成」)

- [ ] `npm run verify`(typecheck && lint && test 相当)の **exit code が 0**(= 単一述語に集約。fixer/reviewer が見る機械ゲートと同一)
- [ ] VISION の全 `[機械]` 条件に対応するテストが緑(ID 照合)
- [ ] (STEP0 で「要る」と判定した場合)対応する Scenario が `features/` にあり、そのタグが VISION の ID 欄に入っている
- [ ] `reviewer` が `NO_ISSUES`
- [ ] (`[AI]` 条件がある場合のみ)AI 検証もすべて pass
- [ ] (A で観測可能な挙動が変わる場合)ビルトインの **verify スキル**で実物を1回動かして観測し、期待どおりであることを確認。非同期生成はローディング表示の消失または実コンテンツの出現まで待ってから観測する(最初に出る骨組み・見出しを待つのは早すぎる)。スタブ/仮データでの実行を「完走の証明」と呼ばない。DB・本番・課金など破壊的副作用が絡む部分は、実行前の利用者確認が優先。

### 完了条件を勝手に緩めない(独立ルール)
「テストを消して緑にする」「条件を削る」「上限を黙って増やす」は**禁止**。詰まったら相談する。

### 検証コマンドが無いとき
`npm run verify` 等が無いリポジトリでは、勝手に設定を書き換えず、以下のいずれかを確認・提案する:
- 既存の `npm test` / `pytest` / `go test` 等を機械的ゲートに採用する。
- `verify` 相当(typecheck && lint && test を1コマンドに)の追加を**提案**し、承認後に作る。
- それも無ければ、最低限「対象テストを実行して exit 0」を暫定ゲートにし、その旨を明記する。

### 暴走防止(かならず守る)
- **往復上限(既定 5)。** 超過、または同じ指摘が2回連続したら **止めて人間にエスカレーション**(無限ループで費用を溶かさない安全弁)。
- **破壊的操作は毎回確認:** push / マージ / 削除 / DB・本番変更 / 依存追加(`package.json` 変更)など。
- **完了条件は改竄しない**(上記ルール)。
- **作業ツリーの変更を破棄しない**:git checkout/restore/reset/stash による巻き戻し禁止(自分の変更の取り消しも Edit の逆適用で)。コミット時は対象パスだけ `git add`(`git add -A` / `git add .` 禁止)。委譲文に「範囲外の変更を破棄しろ」と書かない。

## verify 緑ゲート（このスキル稼働中だけ効く Stop hook）

このスキルの frontmatter `hooks:` に置いた `hooks/verify-gate.sh` が、AI が停止しようとするたびに自動で走る。**loop-engineering 稼働中だけ**効き、global settings には入れていない。

### 何を強制するか

**verify が緑になるまで停止を block すること**だけ。赤先行・ミューテーション・reviewer・VISION 条件の網羅は従来どおり散文の自己規律であり、このスクリプトは強制しない。

### 動作の概要

| 状況 | 動作 |
|---|---|
| VISION ファイル（`VISION.md` or `docs/VISION-*.md` or `docs/vision/*.md`）が無い | 停止を許可（小作業には強制しない） |
| verify コマンドが解決できない | 停止を許可 |
| verify が緑（exit 0） | 停止を許可(自前のブロック回数カウンタもリセット) |
| verify が赤（exit 非0）、自前カウンタが5回未満 | 停止を block し「直して続けて」の理由(失敗ログ抜粋・ログのフルパス付き)を返す。`stop_hook_active` が true でも回数が5未満なら block する(この値は「1回 block した直後」から true になる合図であり「何度も block した」証拠ではないため) |
| verify が赤のまま6回目以降 | 安全弁が開き停止を許可。画面に `systemMessage` で警告(「検証が赤のまま安全弁で停止を許可(5回ブロック後)」)を出す。**この時点で自前カウンタはリセットされる(安全弁の再武装)**ので、次に赤になったエピソードは再び1回目から block される(安全弁が一度開いたきり block に戻らなくなることはない) |
| 自前カウンタ(状態ファイル)の最終更新が既定6時間より古い | 古い回数を持ち越さず、1回目として扱う(セッションをまたいだ回数の誤引き継ぎを防止)。閾値は環境変数 `VERIFY_GATE_STATE_TTL_SECONDS`(秒)で変更できる |

> **注記(タイムアウト):** この Stop hook 自体の既定タイムアウトは600秒(frontmatter の `timeout`)。**超過するとフックはキャンセルされ非ブロッキング扱い=停止は素通しになる**。これとは別に、**verify の実行自体にも自前の制限時間(既定540秒、環境変数 `VERIFY_GATE_VERIFY_TIMEOUT_SECONDS` で変更可)**を設けている。macOS 標準には `timeout` コマンドが無いため、バックグラウンド実行+監視(watchdog)で代替している。この自前の制限を超えた場合は**素通し(無音allow)にはせず**、`systemMessage` で「⚠️ 検証が時間内に完了せず未検証のまま停止を許可」と警告しつつ停止を許可する(未検証のまま許可したことが画面に残る)。

### verify コマンドの解決順

1. `package.json` に `verify` スクリプト → `npm run verify` / `test` スクリプト → `npm test`
2. `pyproject.toml` または `pytest.ini` が存在 → `pytest`
3. `go.mod` が存在 → `go test ./...`
4. `Cargo.toml` が存在 → `cargo test`
5. `Makefile` に `verify` または `test` ターゲット → `make verify` / `make test`

上記いずれも解決できない場合は停止を許可。

### 注意（逃げ道を足さない・意図通りの挙動として明記）

稼働中に verify が赤の間は、**AI がユーザーに質問しようと一旦止まる場面でも停止が block され進み続ける**。これは"止めない"思想の意図通りの挙動であり、質問検知の逃げ道は設けていない。

赤の間に破壊的操作(依存追加等)の利用者確認が必要になったら、**無断で進まず**、確認したい内容を明記して停止を試みる(ブロックが続いても安全弁が開いて止まれる)。**赤のまま安全弁で停止した場合、最終報告は必ず「未完了」形式で、赤のまま停止した事実と理由を先頭に書く**。

## 大規模A(A-大)のオーケストレーション ★規模で分業を上げる

フル(A)の中でも **多ファイル/移行/仕様が重く「1 コンテキストに載らない」規模**のときだけ、計画と実装を別人格に分け、決定的なオーケストレーションに乗せる。**中小規模の A は従来どおりメイン会話でインライン(STEP 1〜6)で十分**——分離はハンドオフで意図(なぜこの述語か・暗黙の前提)が欠落し往復が増えるので、**規模が要求しない限りやらない(過剰オーケストレーション禁止)**。

### 構造(計画→人間ゲート→実装→レビュー→判定)

```
A-中小(1〜数ファイル):従来のインライン STEP 1〜6(計画も実装も同一コンテキスト)
A-大(多ファイル/移行/重い仕様):
  ① Plan エージェント(PMロール・読取専用)が VISION+テスト設計を起草
  ② メインが内容をレビュー → 【人間ブロッキング承認ゲート】で利用者に見せて止まる
  ③ 承認した[機械]条件の赤テストを書き「赤」を目視(=ハンドオフの前提条件)
  ④ loop-eng:implementer が赤→緑の最小実装(workflow `loop-eng:loop-engineering-large-A` の execute)
  ⑤ レビュー往復に委譲(STEP 5 のまま=/loop-eng:review-loop。workflow に入れない)
  ⑥ STEP 6 で verify 再実行 + VISION 全[機械]条件を ID 照合して完了判定
```

### 規模に関わらず全 A で守る 3 つのガード

1. **`[機械]`条件について、赤テストが書けることがハンドオフの前提**。赤が書けない=VISION が曖昧 → **分離せず会話内で直す**(`loop-eng:loop-engineering-large-A` の execute は `[機械]`条件の赤を確認できないと `precondition_failed` で止まる。`[AI]`条件は赤テスト対象外)。
2. **承認ゲートは「VISION 述語に載らない口頭前提・暗黙の微決定」を人間が注入する場**。ここで拾えなかった穴はガード 3 で拾う。
3. **戻りチャネル(★最重要)**。実装中に VISION の穴が判明したら、loop-eng:implementer は**推測で埋めず**ループを抜けて承認ゲートへ戻り VISION を補修する。**同一コンテキストでも独断で VISION を解釈・補修しない**(workflow は `needs_vision_revision` で停止し人間に返す)。

### workflow テンプレ `loop-eng:loop-engineering-large-A`

- 実体はこのプラグイン同梱の `workflows/loop-engineering-large-A.js`(Workflow ツールで `loop-eng:loop-engineering-large-A` として起動)。**2 回に分けて**起動する:
  - `{mode:"plan", goal, scope, focus?}` … Plan を fan-out → **意味的重複の統合 + 抜け漏れ補完 + ID を axis ごとに一意化**して VISION 草案(`visionDraft.conditions`)を返す。fan-out 各エージェントは独立採番するため ID が衝突するが、workflow が統合・振り直し済みで返す(オーケストレータの手作業は不要)。`rawCount`(統合前)/ `consolidatedCount`(統合後)も返る。
  - `{mode:"execute", vision:<承認版>, scope, verifyCmd?, focus?}` … 赤確認(RedGate)→最小実装→verify。`vision` は plan の `visionDraft` を人間が承認・補修したもの。`focus` は重点観点(任意)。
  - **`scope` は配列**(例 `["src/foo.ts", "src/bar.ts"]`)。カンマ区切り文字列を渡しても配列化して受理する。配列/文字列以外は `bad_args`。
- **計画と実装の間に必ず人間の承認ゲートを挟む**。Workflow はバックグラウンド自律実行で**途中に人間ゲートを置けない**ため、ゲートはメイン会話側に置き、**承認済み VISION を execute に渡す**設計(承認なしに実装は始められない)。承認時に、述語に載らない口頭前提・暗黙の微決定を人間が注入してよい(述語の具体化・条件削除は可。新規条件を足したら赤テストを書いて赤を見てから execute する)。
- **module タグは全[機械]条件に付ける(モジュール分割)か、全く付けない(一括)かに統一**する。混在や scope と module の不一致は `bad_args` / `scope_mismatch` で停止する(静かな取りこぼし防止)。
- execute へ渡す承認済み条件には **`userVisible`(真偽値)の宣言が必須**。`true` のときは各[機械]条件に **`scenarioTag`(`@R7` 形式)が必要**で、足りなければ RedGate で止まる(`scenario_gate_failed`)。
- レビュー往復は **workflow に入れず** STEP 5 の委譲先(`/loop-eng:review-loop`)に委譲する(アンチパターン「往復ロジックを自作しない」を守るため)。
- ⚠️ Workflow はサブエージェントを多数起動しトークンを使う。**A-大と判断したときだけ**使い、毎回は使わない。⚠️ `verifyCmd` は編集なしで実行できること(検証は読取専用エージェントが回す)。

#### 返り値 status 早見表(出力をこう捌く)

| status | 意味 | 次の一手 |
|---|---|---|
| `plan_ready` | (plan)VISION 草案ができた | 草案を利用者に見せて承認ゲート → 赤テスト作成 → execute |
| `green` | verify exit 0 + 全[機械]条件が緑 | STEP 5 のレビュー往復に委譲(`/loop-eng:review-loop`。SCOPE を絞るなら `changedFiles`)→ STEP 6 で再 verify + ID 照合 |
| `precondition_failed` | 赤テスト前提が未達 | `missingTests`=新規にテスト / `falsePositives`=書き直して赤を出す → 再 execute |
| `scenario_gate_failed` | シナリオの関門で停止 | 返ってきた不足の一覧を見てシナリオを書く、または見える変化の有無を宣言してから再実行 |
| `needs_vision_revision` | 実装中に VISION の穴が判明(戻りチャネル) | `visionHole`/`conditionId` を見て承認ゲートで VISION 補修 → 再 execute(下記) |
| `verify_failed` | exit≠0 か未緑条件あり | STEP 4 へ戻り修正。緑まではレビューに進まない。条件は緩めない |
| `verify_error` | 検証担当が失敗(実装失敗とは限らない) | verify を再実行(実装は `doneSoFar` で完了済み) |
| `blocked` | 実装担当が続行不能 | `notes`/`conditionId` を見て会話側で対処 |
| `bad_args` / `scope_mismatch` | 入力不備 | メッセージに従い引数/VISION を直す |

#### `needs_vision_revision` が返ったら(戻りチャネルの捌き方)

1. `visionHole` を読み、`conditionId` の条件のどこが曖昧/矛盾/実装不可かを把握する。
2. 承認ゲートに戻り、その条件の述語を具体化する(書き直した赤テストが書けるまで)。
3. 修正版 VISION **全体**(直さない条件も含める)で `{mode:"execute", vision:<補修版>, scope, verifyCmd}` を再実行。`doneSoFar` の済みモジュールは触らない。
4. **同じ穴で 2 回続けて止まったら**、条件分割 or `[AI]` 化を検討し、止めて利用者に相談(独断で埋めない)。

## 最終報告フォーマット

### 完了した場合
```markdown
## クローズドループ完了報告
- 結果: ✅ 完成
- 対象(SCOPE): <…>
- 機械的ゲート: npm run verify = exit 0 ✅
- VISION 条件: N1✅ E1✅ B1✅ S1✅ (Q1✅) ※×があれば明示
- Scenario: 要/不要(理由) / `features/<file>` の @X1
- reviewer: NO_ISSUES ✅
- AI 検証: pass ✅(該当あれば)
- 実物起動観測: 済/対象外
- 往復回数: N / 5
- 変更ファイル(コミットは指示待ち): src/… , test/…
```
> コミット/push は**しない**(明示依頼があってから)。コミットや PR 作成は各自の手順で行う。
> ※司令塔(loop-eng:coding-orchestrator)経由の運用では「1タスク→レビュー→コミット」の都度コミットを優先してよい。

## 詰まったときの逃げ道(初心者を一人にしない)

| 状況 | あなた(Claude)の対応 |

| 何を作りたいか言葉にできない | 似た例を 2〜3 個出して選ばせる。ゼロから言わせない。 |
| VISION 条件が「測れない」言い方 | その場で「○× が言える形」に一緒に書き換える(例を見せる)。 |

## やってはいけないこと(アンチパターン)

- ❌ VISION を書かずにいきなり実装する(止め時が無くなる)。
- ❌ 利用者から見える変化があるのに Scenario を書かずに実装する(あとで QA 仕様書にまとまらない)。
- ❌ 述語が曖昧(「使いやすく」「ちゃんと」)。○× が付かない条件は条件ではない。
- ❌ 機械で測れるものを `[AI]` にする(非決定的になり回帰検知が壊れる)。
- ❌ 赤を一度も見ずにテストを「通った」とする(偽パスの温床)。
- ❌ スタブ/仮データの E2E や生成途中の画面の観測を「実物の完走確認」と呼ぶ。
- ❌ 機械的ゲートが赤(exit 非0)なのに AI 採点に進む / 見た目を褒める。
- ❌ 同じ AI に実装と採点を両方させる(maker = checker)。
- ❌ レビュー往復ロジックを自前で書く(`/loop-eng:review-loop` に委譲する)。
- ❌ `/loop-eng:review-loop` を `Skill(...)` で呼ぼうとする(スラッシュコマンドである)。
- ❌ VISION/verify 照合を reviewer に任せたつもりになる(reviewer はコード品質しか見ない。照合は自分でやる)。
- ❌ 完了条件を満たせないからとテストを消す・条件を削って緑にする。
- ❌ 依頼範囲を超える破壊的操作(commit/push/マージ/削除/DB/本番/依存追加)を独断で行う。
- ❌ 作業ツリーの変更を git checkout/restore で破棄する(人の意図的な編集ごと消える)。
- ❌ 中小規模の A でまで計画を別人格に切る・Workflow を使う(過剰オーケストレーション。ハンドオフで意図が欠落し往復が増える)。
- ❌ 大規模A で計画の人間承認ゲートを飛ばして実装に入る / 赤テストを見ずに別人格へハンドオフする。
- ❌ 実装中に判明した VISION の穴を独断で解釈して埋める(戻りチャネルで承認ゲートに戻す)。
- ❌ レビュー往復を workflow の中に自作で組み込む(STEP 5 の委譲先=`/loop-eng:review-loop` に委譲する)。

## クイックリファレンス(毎回守る要点)

0. まず **適用判断(A/B/C)**:些末・使い捨て・テスト不可は **C(省略)**、小変更は **B(ミニ)**、ちゃんとした機能・バグ修正は **A(フル)**。毎回フルを強制しない。A の中でも **中小はインライン / 大規模(多ファイル・移行・重い仕様)だけ** 計画を Plan に分離+人間承認ゲート+workflow `loop-eng:loop-engineering-large-A`。規模が要求しない分離はしない。実装中の VISION の穴は**戻りチャネル**でゲートに戻す。
1. 実装より先に **VISION.md(機械でも ○× 判定できる述語 + ID + 検証手段タグ)** を書く。**利用者から見える変化があるなら、さらに先に `features/` の Scenario を書き、そのタグを VISION の ID に使う。**
2. **VISION の行 = 観点表の行 = テスト1個** を同じ ID で貫通。4〜5 軸(正常/異常/境界/状態/エラー)は出発点。
3. テストは **先に赤を見てから緑**。後付けはミューテーションで検出力を証明。
4. 土台は **機械的検証(exit 0)**。AI 検証は曖昧な品質だけ上乗せ。
5. 「作る↔確認」往復は **`/loop-eng:review-loop` に委譲**(自作しない)。全タスク完了後に `START_SHA..HEAD` の通しレビューを1回。SCOPE/FOCUS/最大回数を渡す。
6. **VISION 照合と verify は自分(STEP6)でやる**。reviewer は見てくれない。完了 = verify exit 0 + 全[機械]条件が緑 + NO_ISSUES(必要なら AI 検証も)。照合は存在と緑だけでなく**assert が述語の本質を検証しているか読み比べる**(弱い代理assertは不合格)。観測可能な挙動が変わる場合は**実物を1回動かして観測**するところまでが完了判定。
7. 往復は **上限 5 回**。超過・同一指摘2連続は **止めて人間に相談**。破壊的操作は **毎回確認**。
8. 初心者を一人にしない。各 STEP で「✅ これが出たら次へ」を確認し、詰まったら逃げ道を出す。
